# 05｜服务端状态、事件协议、成就规则、可回放测试

## 核心不变式

1. **存档先有唯一事实，后有叙事文字**。一次状态变更先通过引擎校验、原子提交 canonical event，再向 AI 请求叙述。
2. AI 提交的是 `NarrativeProposal`，不能直接调用数据库写入、不能修改 `UnlockRecord`、不能发放奖励。
3. 所有成就只根据**不可伪造的事件**验证。一个事件在同一用户成就解锁最多一次，事件重试不会叠加。
4. `runId`、`actorId`、`roomId`、`accountId` 明确区分；队伍、角色和账户不是同一个主键。
5. 某角色不可逆后果需要自身控制者确认；QTE 操作结果不能绕过角色安全机制。
6. **历史事实不可悄悄删除**；改变状态需要新的合法事件，旧事件仍供编年史和调试。

## 建议最小模块

```text
src/game/systems/events/         event schema, reducer, validation, replay
src/game/systems/achievements/   catalog, evaluator, unlocks, progress
src/game/systems/interaction/    six templates, guard, results
src/game/systems/chronicle/      event selection, redaction, summaries
src/ui/achievement/             Gallery, Card, Detail, Toast, EndingSummary
src/ui/interaction/             InteractionOverlay and templates
server/                         authoritative room commit, unlock persistence
```

这是推荐目录，不是要求直接重排当前文件。新系统应先提供 adapters，让旧 `GameState` 继续可玩，然后渐进迁移。

## 成就 DSL 结构

`achievements.v1.json` 中每条 rule 形如：

```json
{"op":"event","type":"core_arc_resolved","where":{"arcId":"gray_well"}}
```

```json
{"op":"count","type":"npc_rescued","min":3,"distinctBy":"subjectId"}
```

```json
{"op":"all","rules":[
 {"op":"event","type":"faction_treaty_signed","where":{"treatyId":"kalvis_ember_peace"}},
 {"op":"event","type":"npc_oath_kept"}
]}
```

- 仅支持已定义的操作和事件 type；字段 `where` 为等值匹配，若需要比较范围将属性预先规范化为等级/枚举或写专门判定器。
- `count` 是匹配的**独立事件**数；`distinctBy` 是去重键；`sameRun=true` 默认；同时判断本局多条事件时要固定 runId。
- 个体归因 `scope=character` 要求事件 `actorIds` 含该角色；`scope=party` 要求事件归属队伍/多人房间；`scope=run` 是本局真实达成。账户解锁只是将本局成就落入长期档案。
- `any`/`all` 必须严格对每项规则求值，不允许 AI 直接返回 `true`。

## 事件类型建议（首版）

- 主线：`run_started`, `act_entered`, `core_arc_resolved`, `truth_verified`, `world_clock_stabilized`, `ending_committed`, `world_crisis_prevented`, `world_policy_changed`。
- 人物：`npc_met`, `npc_rescued`, `npc_name_restored`, `npc_oath_kept`, `npc_belief_changed`, `npc_reconciled`, `npc_protected`, `npc_farewell_kept`, `faction_treaty_signed`, `mediation_success`。
- 探索：`region_visited`, `place_discovered`, `bell_city_verified`, `memory_fragment_verified`, `route_discovered`, `historical_record_verified`, `clue_chain_solved`, `interaction_completed`, `artifact_verified`, `world_truth_confirmed`。
- 沙盒：`player_project_created`, `player_project_milestone`, `trade_route_established`, `business_profitable`, `civic_service_operational`, `player_organization_created`, `custom_resolution_verified`, `home_established`, `team_goal_completed`。
- 传奇：`ancient_name_rest`, `world_rescue_verified`, `ending_committed`, `cross_faction_peace_verified`, `legend_recognized`, `bell_ring_prevented`, `nonviolent_crisis_resolved`, `all_bells_considered`, `historical_falsehood_corrected`。
- 同一行为可以包含一组事件，但发出前要统一事务和因果 sourceId。若同一事实被两个类型表达，需定义去重策略，防止刷次数。

## 成就与编年史写入顺序

1. Server/solo rule engine 接收一个合法意图；校验当前回合、角色权限、物品、地点、条件、风险确认。
2. 计算 StateTransition，生成 canonical events（包含唯一 `eventId`）。
3. 用同一 `runId` 读最新事实，应用事件并持久化；网络/房间版本冲突重试或拒绝。
4. 使用成就 evaluator 根据规则计算新解锁； `(accountId, achievementId)` 唯一键；另记 `(runId, actorId?, achievementId)` 首次达成。
5. AI 仅基于**已提交的新状态**生成文本；AI 不可反向改变解锁结果。
6. Toast 在 UI 空闲时呈现；若断线，重连依据 unlockId 去重恢复通知。

## 未来 DB 表建议

```text
narrative_event(id PK, run_id, seq, type, actor_ids_json, subject_id,
                region_id, payload_json, source_intent_id, schema_version, committed_at)
achievement_unlock(id PK, account_id, achievement_id, first_run_id,
                   first_actor_id, source_event_ids_json, unlocked_at,
                   verified, UNIQUE(account_id, achievement_id))
run_achievement(run_id, achievement_id, actor_id_nullable, source_event_ids_json,
                achieved_at, UNIQUE(run_id, achievement_id, actor_id_nullable))
chronicle_entry(id PK, run_id, event_ids_json, title, story_text,
                visibility, generated_by_model, reviewed, created_at)
interaction_instance(id PK, run_id, scene_id, actor_id, template, phase,
                     seed, outcome_id, version, created_at, updated_at)
```

生产表结构根据现有 Cloudflare / 数据库基础设施调整。无账户登录的游客需要本地档案 ID、可导出数据和未来绑定账号的合法合并规则；不能将 `localStorage` 视为安全权威。

## 单元测试最低清单

- catalog：50 个唯一 ID、有效分类、合法 rarity、合法 rule AST、存在 SVG/PNG 图标、无重复名称/冲突隐藏字段。
- predicate：`event`, `all`, `any`, `count`, `distinct`，同 run 跨 actor，已解锁/未解锁状态。
- idempotence：相同 `eventId` 重放多次解锁数量不增加；同一账号跨局只入账一次，单局再次达成仍记录。
- race：联网双击/重复发送 QTE 同一 `interactionInstanceId` 不能重复生成事件；同一房间两玩家并发处理不丢操作。
- privacy：秘密成就服务端输出给未达成用户不得包含真名/图标资源路径/解锁条件；分享导出剔除敏感字段。
- narrative consistency：NPC 已死亡无法朗读在世固定台词；未持钟心不展示全部钟心；封印成功后不能朗读“第七声响起”。
- ending：D02 无灾难前提不入候选；D17 无条件不入候选；可用候选不足 3 个不报错；负数权重无非法随机。
- qte：skip 可完成等价路径；低动作要求、键盘、触屏可操作；重复触发/离线恢复不会反复扣物品。
- save：旧版不能兼容时明确提示；个人账户成就不能被旧局删除；版本升级恢复或拒绝明确。
- UI：mobile 320px、375px、768px、desktop 1280px；焦点回归、toast 不抢焦点、分页不跳页、prefers-reduced-motion。

## 人工试玩验收（推荐基准）

- **沙盒玩家**：在灰港 35+ 次有意义行动建立商铺，世界事件照常发展，结局保留事业成果。
- **硬核破局玩家**：破坏商会/偷钟心/逃走，再返回，文本和 NPC 行动不自相矛盾。
- **NPC 情感玩家**：追踪救命恩、背叛、信念改变；旧事不会被最新三条印象覆盖。
- **低动作要求玩家**：通过可跳过或无障碍操作完成 6 类互动，不受手速惩罚。
- **多人**：中途加入/离开、个人成就与队伍共同成就、断线重连、结局同步、成就唯一性。
