# 项目核心准则：12 条最高标准

本文件是整个 Dungeon 项目唯一的核心准则正文，适用于需求分析、设计、编程、修复、重构、测试、规则制定，以及 Codex 对 WorkBuddy 的派工、审核和返工。项目内其他规则和子目录规则必须遵从本文件；平台指令、安全边界及用户当前明确要求仍优先。已有方案不等于实现授权。

## 来源与适用方式

- 第 1–4 条依据 [Karpathy 编程原则仓库](https://github.com/multica-ai/andrej-karpathy-skills)。
- 第 5–12 条依据 [Mnilax 的补充文章](https://x.com/Mnilax/status/2053116311132155938)（[长文地址](https://x.com/i/article/2053106718226227203)）。
- 本文为结合项目执行边界的中文改写，保留全部 12 条规则。2026-11-10 已通过公开帖子接口读取文章正文及规则块；X 网页直接抓取返回 403。
- 采用可执行的行为标准，不将文章自报的错误率、合规率或行数阈值当成本项目的实测结论。保持本文精简，具体任务细节放任务文件。

## 1. 先思考再编码

明确目标、范围、重要假设和取舍。存在影响实现的多种解释时先澄清，不默默选择；遇到更简单方案应提出。无法理解关键要求时先说明问题，明确且简单的任务直接执行。

## 2. 简单优先

采用满足当前需求的最小实现。不得添加未要求的功能、单次使用的抽象、预留配置或不可能场景的防御代码。方案过大时缩小到可独立验收的一步，不以代码量或复杂度作为成果。

## 3. 精准修改

每处改动都应追溯到当前任务与授权范围。不得顺手重构、格式化或清理无关代码；只清理本次修改造成的未使用代码。保护既有未提交改动，发现其他问题先报告。

## 4. 以可验证目标推进

先定义成功表现和检查方法，再执行并验证。缺陷修复优先复现，重构核对前后行为；验证失败时修复或明确报告阻塞。简单文档和明显单行修正可直接检查，不机械增加测试和流程。

## 5. 模型只承担需要判断的工作

将模型用于理解语言、分类、起草、总结及非结构化信息提取。已有确定规则的路由、重试、状态码处理、计算和数据转换由代码或现有工具执行；不得用模型猜测替代确定性逻辑。

## 6. Token 预算必须执行

默认每个执行任务 4,000 tokens、每个执行会话累计 30,000 tokens；用户或更高优先级指令明确指定时采用其预算。派工时注明预算，返工计入同一会话累计量，不换任务 ID 绕过预算。

接近上限时先保存目标、已尝试方案、验证结果与剩余事项，再缩小任务或从明确检查点接续；达到上限不得静默超支，应报告并结束该执行单元。预算调整必须显式说明。

有用量数据时记录实际值；无可靠计量时明确标记估算与计量限制，提前收束，不声称已技术强制限额。新会话必须读回检查点，不靠丢失上下文重新尝试。

## 7. 显式处理冲突，不折中拼接

发现两套实现、模式或规则冲突时先指出差异。依据适用范围、已执行的项目约束、测试覆盖及新旧关系选择一套并说明依据；无法判断时澄清。不得同时叠加相互矛盾的方案，其他模式列为待处理事项。

## 8. 先读再写

修改前读取目标文件、导出接口、直接调用方和相关共享工具，确认已有实现及依赖关系；同时读取交接和历史日志。没有读过的内容不得声称已理解，关键结构不清楚时先查证或询问，避免重复实现。

## 9. 测试验证意图

测试应体现需求为何重要，并能在关键业务约束被破坏时失败。避免只断言非空、只复刻实现或硬编码预期制造通过；覆盖与当前任务相关的正常、失败和边界场景。不得删测试、放宽断言或忽略失败来换取通过。

## 10. 每个重要步骤保留检查点

多步骤任务在重要阶段后记录已做事项、已验证结果、剩余事项及风险。必要内容落到任务文件、CONTINUE.md 和当天修改日志。无法准确描述当前状态时先重建检查点，不在未知或失败状态上继续叠加修改。

## 11. 遵循代码库惯例

遵从当前模块既有命名、组件模式、错误处理和测试习惯。个人偏好不得成为引入另一套风格或依赖的理由；认为惯例有害时说明具体影响，另行提出变更，不偷偷分叉。局部惯例冲突按第 7 条处理。

## 12. 失败与不确定性必须可见

明确报告失败、跳过、部分成功、未验证和能力限制。测试报告列出通过、失败与跳过及原因；存在跳过时不得笼统称全部通过。不得将提交受理、执行结束、文件存在或自报完成等同于功能验收成功。

## Codex 与 WorkBuddy 的执行及审核门槛

- 每次派工与返工携带本文件全文，明确目标、allowedPaths、预算、成功标准及交付证据；客户端自动附带全文属于提示约束，不是沙箱或合规证明。
- Codex 读取实际成果和完整 diff，按第 1–12 条逐项记录“通过 / 需返工 / 未验证 / 不适用”及简短依据；不适用必须说明原因，不用清单代替实际核查。
- 核查范围包括：假设与取舍、最小方案、改动范围、成功标准、确定性逻辑、预算、冲突处理、阅读依据、测试意图、检查点、代码惯例及真实结果。
- 关键项需返工或未验证时不得标记最终验收通过；给出具体文件、问题和最小返工要求，返工后重新验证。
- 既有待审成果同样按 12 条复核；无法补证的历史行为标为未验证，不伪造追溯记录，不重发已开始任务。
- 费用、权限、本机隐私和任务状态继续遵从 WorkBuddy 协作规范；每轮简报记录实际执行者、模型、任务/轮次、产物、检查结果与未完成项。
