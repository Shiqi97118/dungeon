# 13｜代码代理任务书（分工、分支、异步协作与任务卡）

> 给所有参与的代理和用户看。规格以 `12-开工规格.md` 为准；本篇只规定**谁做什么、在哪里做、怎样交接、怎样算完成**。实时状态写在 `docs/协作看板.md`。

## 1. 分工

| 角色 | 做什么 | 不做什么 |
|---|---|---|
| **用户** | 决定合并到 `feat/local-workbuddy-handoff`、`main` 与发布；回答看板里的“待决问题” | — |
| **Cursor（Claude，云端代理）** | **唯一写游戏代码的代理**：`src/`、`server/`、`worker/`、测试、构建配置；维护剧情规格（`docs/story/` 的 `02`–`13`、`data/`、`tools/`）；在单独的时间段异步工作，一次会话做一张任务卡 | 不合并到 `main`、不部署、不改密钥、不动 `.local/` 和登录凭据；不碰 WorkBuddy 的产出目录 |
| **Codex（本地）** | 集成与审核：拆分与核对任务、审 Cursor 的 PR（按 12 条准则逐项记录）、在本机跑测试与试玩、合并已审核的任务 PR 到集成分支（需用户授权，见第 2 节）、维护看板和总交接；指挥 WorkBuddy | **不写游戏代码**；发现代码问题写进 PR 评论或看板，由 Cursor 修 |
| **WorkBuddy（由 Codex 派工）** | 插图与视觉素材、交互模板的视觉稿、手机与电脑上的试玩执行、文本迁移的初稿 | 不写游戏代码；不 push、不发布；完成只表示“待 Codex 审核” |

WorkBuddy 的派工、模型、费用和验收继续遵从 `docs/workbuddy/协作规范.md`。

## 2. 分支

```
main（合并即自动发布到线上）
 └─ feat/local-workbuddy-handoff（PR #4，开工期间不合并到 main）
     └─ feat/iselan-v1（新建的集成分支，所有新剧情代码汇集在这里）
         ├─ cursor/<任务>-034a（Cursor 的任务分支，一张任务卡一个）
         └─ codex/<任务>、workbuddy/<任务>（Codex / WorkBuddy 的任务分支）
```

- 开工第一步（任务 OPS-00）：把 PR #5（剧情文档）和 PR #6（设计包）合并进 `feat/local-workbuddy-handoff`，再从它切出 `feat/iselan-v1`。这两次合并都不会发布到线上。
- 任务 PR 一律以 `feat/iselan-v1` 为目标。合并到 `feat/iselan-v1` 不发布；只有用户把它一路合并到 `main` 才发布（任务 REL-01）。
- **Codex 的合并权限（用户 2026-11-11 授权）**：Codex 可以把任务 PR 合并进 `feat/iselan-v1`，条件是全部满足：
  1. PR 已标为“可审核”，Codex 在 PR 里留了“通过”的审核记录；
  2. 第 5 节的检查在 Codex 本机复跑全部通过；
  3. PR 的目标是 `feat/iselan-v1`，且没有改 `docs/product/narrative-v1/`、`.local/` 或任何密钥；
  4. 用“合并提交”方式合并（不压缩、不变基），合并后删除任务分支并更新看板。
- 改了 `wrangler.jsonc` 或新增 D1 表的 PR 照常合并，但 Codex 在看板“待决问题”记一条，发布前由用户确认。
- 任何代理都不能合并自己写的 PR，也不能合并进 `feat/local-workbuddy-handoff` 或 `main`；这两步只由用户决定（任务 REL-01）。
- 同一个分支任何时候只由一个代理、在一台电脑上修改。

## 3. 异步协作流程

### 3.1 领取任务卡（每次会话开始）

1. 拉取 `feat/iselan-v1` 的最新提交；读 `AGENTS.md`、`docs/编程与审核原则.md`、本篇、`12-开工规格.md`、`docs/协作看板.md` 和当天及之前的修改日志。
2. 查看 GitHub 上所有打开的 PR（`gh pr list`）。**打开的草稿 PR 就是“已领取”**：标题以 `[卡号]` 开头的卡已被人占用，不能再领。
3. 选看板中第一张“待领”且依赖都已“完成”的、属于自己的卡；用户指定了卡号时做指定的卡。
4. 建任务分支，推一个最小提交，**立刻开草稿 PR**，标题 `[卡号] 简述`，正文写本次会话的计划。这一步就是领取，其他代理看得到。

### 3.2 做的过程中

- 只改任务卡“改动范围”里列出的路径。需要改范围外的文件时，在看板“待决问题”里写明，不顺手改。
- 每完成一个可测的小步骤就提交；测试通过后再推送。
- 遇到规格不清或互相矛盾：按 `12` 开头的优先级处理；仍不清楚就写进看板“待决问题”，在 PR 里标明“按某种理解先做，待确认”，不自行扩大范围。

### 3.3 收尾（每次会话结束，即使卡没做完）

1. 跑完第 5 节的检查，把命令和结果贴进 PR 正文。
2. 更新当天修改日志 `修改日志/YY-MM-DD.md`：在文件末尾加一节 `## 代理 · 卡号`，只写实际完成的内容（多人同日编辑时保留双方的段落）。
3. 更新看板里这张卡的状态与“最后进展”。
4. 写本代理的交接：Cursor 写 `交接/cursor.md`，Codex 写 `交接/codex.md`（按 Jiaojie 技能 EXPORT，内容包括停止点、下一步、未验证项）。根目录 `handoff.md` 是总交接，**只由 Codex 在合并后更新**，避免两边同时改同一文件。
5. 卡已完成：PR 改为“可审核”。没做完：保持草稿，正文写清停在哪里。

### 3.4 审核与返工

- Codex 按 12 条准则和任务卡的“验收”逐项审核，在 PR 里留言：通过 / 需返工（列出具体问题和复现方式）。
- Cursor 下一次会话先处理自己名下“需返工”的 PR，再领新卡。
- 审核通过后由 Codex（已授权时）或用户合并进 `feat/iselan-v1`，Codex 更新看板与总交接。

## 5. 每张卡的完成标准

- 依次通过：`npm ci`、`npm run lint`、`npm test`、`npm run build`、`node docs/story/tools/check-texts.mjs`。
- 新规则有单元测试；不删除测试、不放宽断言。
- 界面改动附手机与电脑的截图；联机相关改动说明断线与重复提交的处理。
- 当天修改日志、看板、本代理交接都已更新；PR 正文列出测试命令与结果、已知问题、范围外未做的事。
- 不合并到 `main`、不部署、不充值、不改密钥。
